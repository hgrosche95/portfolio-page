Eine Chat-App, die Reisen plant: Man beschreibt Ziel, Zeitraum, Budget und Vorlieben, und der Agent stellt bei Bedarf Rückfragen, sucht (simulierte) Flüge und Hotels und speichert am Ende einen strukturierten Tagesplan in der Datenbank. Fragt man stattdessen etwas zum Reiseziel selbst, zum Beispiel was man in Lissabon essen sollte, durchsucht der Agent eine eigene Wissensbasis und antwortet mit Quellenangabe, statt aus dem Gedächtnis zu spekulieren. Gebaut als Lernprojekt für produktionsnahe LLM-Anwendungen: Tool-Use-Agenten, Retrieval-Augmented Generation, austauschbare LLM-Anbieter, ein eigener MCP-Server und automatisierte Qualitätsmessung.

**Warum so gebaut:** Das Kernstück ist kein einzelner Prompt, sondern eine echte Agent-Schleife: Das Backend ruft das LLM mit einem `tools`-Array auf, führt angeforderte Tool-Calls aus (`search_flights`, `search_hotels`, `save_itinerary`, `search_travel_knowledge`) und gibt die Ergebnisse als `tool_result` zurück, bis das Modell keine weiteren Tools mehr braucht. Die Wissenssuche ist dabei bewusst ein Tool und keine starre Vorschaltsuche vor jeder Anfrage: Das Modell entscheidet selbst, wann eine Faktenfrage vorliegt, statt jede Nachricht unabhängig vom Inhalt erst durch die Suche zu schicken. Der LLM-Aufruf selbst läuft hinter einer eigenen Provider-Schnittstelle mit Retry-Wrapper: Groq ist der Produktions-Default (kostenloses Tier), Anthropic bleibt als umschaltbarer Fallback über dieselbe Schnittstelle erreichbar. Ein Anbieterwechsel ist damit eine Konfigurationsänderung, keine Code-Änderung.

**Technisch interessant:** Die Wissenssuche läuft als eigener Python/FastAPI-Service statt als In-Process-Bibliothek im NestJS-Backend, weil das Embedding-Ökosystem (hier `fastembed`, lokal über ONNX, ohne API-Key und ohne laufende Kosten) in Python lebt und die Agent-Orchestrierung in TypeScript: eine dokumentierte HTTP-Schnittstelle zwischen beiden statt eines Sprachkompromisses für alles. Jeder Agentenlauf wird zusätzlich als Langfuse-Trace aufgezeichnet, allerdings bewusst ohne Freitext-Inhalte: Getraced werden nur Modellname, Token-Zahlen, Latenz und welche Tools mit wie vielen Treffern liefen, nicht die Nutzernachricht oder die Antwort selbst, da beide Reisepräferenzen enthalten können. Dieselben Fähigkeiten (Wissenssuche, Reiseplan anlegen und auflisten) stehen außerdem über einen eigenen MCP-Server zur Verfügung, nutzbar direkt aus Claude Code oder Claude Desktop; das Löschen eines Reiseplans existiert bewusst nur als REST-Endpunkt und nicht als MCP-Tool, damit ein Modell nicht autonom unwiderruflich Daten löschen kann. Ob RAG und Tool-Auswahl überhaupt funktionieren, ist keine Meinung, sondern wird von einem eigenen Eval-Harness gegen ein festes Golden Dataset gemessen (Recall@k, MRR, Tool-Genauigkeit), das nachts automatisch gegen den echten Stack läuft und als CI-Artefakt landet.

**Deployment:** Vollständig als Infrastructure-as-Code über Bicep-Module nach Azure. Static Web Apps fürs Frontend, zwei Container Apps in derselben Environment für NestJS-Backend und RAG-Service (beide mit Skalierung auf null), wobei der RAG-Service ohne öffentliche Erreichbarkeit läuft und nur intern über seinen Namen erreichbar ist. Dazu Application Insights mit einem eigenen `ItinerarySaved`-Event für echtes Produkt-Tracking statt nur Standard-Request-Logging. Die Datenbank läuft auf Neon statt auf einem selbst verwalteten Azure-Postgres: eine verwaltete `DATABASE_URL` aus einem Secret statt eigener Firewall-Konfiguration und Bicep-Modul für die DB. Der Login gegen Azure für den Deploy läuft über OIDC (Federated Credentials), ganz ohne langlebigen Secret-Schlüssel.
