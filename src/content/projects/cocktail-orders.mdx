Eine Bestell-App für die eigene Cocktail-Party: Gäste öffnen die Seite, loggen sich nur mit Namen ein, bestellen aus einer filterbaren, filmklassiker-themed Cocktail-Karte und sehen live, wie viele Bestellungen noch vor ihrer dran sind — oder beschreiben ihren Wunsch in eigenen Worten ("etwas Bitteres, ohne Rum, ohne Eis"), den ein LLM in einen passenden Menüeintrag übersetzt. Auf einem Tablet läuft eine passwortgeschützte Barkeeper-Ansicht mit allen offenen Bestellungen samt Rezept, die Zutaten als "nicht vorrätig" markieren kann; betroffene Cocktails verschwinden dann automatisch aus der Gästekarte. Bewertete Cocktails fließen außerdem in eine "Empfohlen für dich"-Sektion pro Gast ein.

**Warum so gebaut:** Zwei unabhängige Node-Projekte statt eines Monolithen: ein React/Vite-Frontend und ein schlanker Express-Server. Die Freitext-Bestellung läuft bewusst als klar abgegrenzter Schritt statt als offener Chat: Ein einzelner LLM-Aufruf ordnet den Wunsch entweder eindeutig einem Cocktail zu (inklusive Hinweisen wie "ohne Eis", die direkt ins Notizfeld übernommen werden) oder liefert bei Mehrdeutigkeit eine Auswahlliste zurück — bestätigt wird am Ende immer über das normale Bestellformular, nie direkt aus dem Freitext heraus. Das Frontend erkennt selbstständig, von welchem Host es geladen wurde, wodurch es ohne Konfiguration auch im lokalen WLAN funktioniert.

**Technisch interessant:** Die Echtzeit-Synchronisierung ist bewusst einfach gehalten. Der WebSocket-Server sendet bei jeder Änderung nur ein kurzes `'orders-changed'`-Signal, keine Nutzdaten. Clients holen sich den aktuellen Stand dann per normalem REST-Call — kostet einen zusätzlichen Roundtrip, macht die Synchronisierung dafür aber deutlich einfacher und weniger fehleranfällig als vollen State über den Socket zu schicken. Welche Cocktails bestellbar sind, wird nicht gespeichert, sondern aus den als "nicht vorrätig" markierten Zutaten und den Rezepten live berechnet. Die "Empfohlen für dich"-Sektion läuft über klassisches Collaborative Filtering auf den Bewertungen anderer Gäste, ohne LLM. Die Barkeeper-Ansicht ist nicht nur in der Oberfläche geschützt: Der Login liefert ein signiertes Token mit Ablaufzeit, und jede Barkeeper-Aktion wird serverseitig dagegen geprüft. Bestellungen validiert der Server ebenfalls selbst (eine offene Bestellung pro Gast, Positionen aus der eigenen Karte statt aus dem Request), und der Prompt für die Freitext-Bestellung wird nur aus der Server-Kopie der Karte gebaut, nie aus Client-Daten. Erreicht Groq während einer Session sein Rate-Limit, wird die Freitext-Funktion für den Rest der Session sauber deaktiviert statt Fehler zu werfen oder endlos zu retryen.

**Deployment:** Frontend als Azure Static Web App, Backend als Container App mit Skalierung auf null (Image über GHCR), Datenbank auf einem extern verwalteten Postgres — alles über Bicep als Infrastructure-as-Code bei jedem Push nach `main` neu ausgerollt. Die Kaltstart-Wartezeit nach einer Ruhephase lässt sich vorab über den Status neben dem Live-Button oben prüfen.

**Aktueller Stand:** Fertig nutzbar, mit CI-Pipeline (Lint/Test/Build für Frontend und Backend parallel), geschütztem `main`-Branch und Tests gegen eine echte Postgres-Instanz via Supertest.
